Title: Client discards the buffered response body when the server follows END_STREAM with RST_STREAM(NO_ERROR)
Labels: bug
Refs: H2-10

## Summary

`Reset_Stream` flips any stream it can still find to `Failed`, including one whose response has already ended with END_STREAM and whose body is sitting in the response buffer. `Read` tests the failure before the buffered bytes, so the body is never handed out and `Read_Body` raises `Protocol_Error`. RFC 9113 names this exact sequence as permitted and forbids a client from discarding the response because of it. Go's HTTP/2 server sends it whenever a handler finishes while the request stream is still open.

## Problem

Commit `f078732`.

`Reset_Stream` looks the stream up with `Find`, which excludes only `Free` slots, and then fails it regardless of the error code and regardless of whether the response already completed (`src/flyology-http-http_2_client_connection.adb:1370-1387`):

```ada
      procedure Reset_Stream
        (Stream_ID : Frames.Stream_Identifier;
         Error     : Frames.Error_Code)
      is
         Index : constant Natural := Find (Stream_ID);
      begin
         if Index = 0 then
            return;
         end if;
         Streams (Index).Response_Observed := True;
         Streams (Index).Failure :=
           (if Error = Frames.Refused_Stream
              and then not Streams (Index).Head_Available
            then Refused_Failure
            else Other_Stream_Failure);
         Streams (Index).Phase := Failed;
```

`Read` tests the failure before it looks at what is buffered (`src/flyology-http-http_2_client_connection.adb:1522-1531`):

```ada
            if Item.Failure = Connection_Failure then
               Result := Body_Connection_Failed;
               return;
            elsif Item.Failure = Response_Protocol_Failure then
               Result := Body_Protocol_Failed;
               return;
            elsif Item.Failure /= No_Failure then
               Result := Body_Stream_Failed;
               return;
            elsif Item.Response_Count > 0 then
```

The synchronous reader turns `Body_Stream_Failed` into an exception (`src/flyology-http-client.adb:7226-7227`, `raise Protocol_Error with "HTTP/2 response stream failed before body completion";`) and the composable driver maps it to `Response_Invalid` (`src/flyology-http-client.adb:4473-4474`). The response head itself survives, because it was published before the reset arrived, so a caller sees the correct status and then an exception instead of the body.

The reset is reliably in the same read burst as the response, because the synchronous driver deliberately keeps parsing after the stream becomes ready (`src/flyology-http-client.adb:7004-7010`):

```ada
                     when H2_Connections.Pump_Progress =>
                        --  Keep draining the already-readable transport burst
                        --  after this stream becomes ready. Otherwise a
                        --  synchronous body reader can consume the
                        --  descriptor's edge, hand the shared pump to a
                        --  lightweight sibling, and strand buffered frames.
                        null;
```

RFC 9113 section 8.1: "a server MAY request that the client abort transmission of a request without error by sending a RST_STREAM with an error code of NO_ERROR after sending a complete response (i.e., a frame with the END_STREAM flag set). Clients MUST NOT discard responses as a result of receiving such a RST_STREAM".

Go's HTTP/2 server does this deliberately. `golang.org/x/net/http2/server.go:1218-1235` at v0.57.0, the module version present in this machine's Go module cache, reads:

```go
		switch st.state {
		case stateOpen:
			...
			st.state = stateHalfClosedLocal
			// Section 8.1: a server MAY request that the client abort
			// transmission of a request without error by sending a
			// RST_STREAM with an error code of NO_ERROR after sending
			// a complete response.
			sc.resetStream(streamError(st.id, ErrCodeNo))
```

The same code is bundled into Go's standard `net/http` (`src/net/http/h2_bundle.go` in go1.23.4), which is what `tests/interop/http2_go_peer.go` uses and what `scripts/http2-interop.sh:77-78` builds. Any Go handler that answers without reading the request body, such as an authentication rejection, a 413, or an endpoint that ignores the body, produces the sequence.

No maintained suite covers it. The `early-final` and `early-final-body` scenarios in `tests/http2_peer.py:170-183` send the same early response without a reset, because python-hyper h2 does not send one on its own; the Go handler in `scripts/http2-interop.sh` reads the whole body, so Go never resets there; `tests/flyology-http-http_2_client_connection-smoke.adb` has no RST_STREAM case at all; and h2spec does not test clients.

## What happens now

Spike: a raw HTTP/2 server peer answers a POST with a complete 413 response and the permitted reset in one write, `HEADERS(:status 413) + DATA("rejected", END_STREAM) + RST_STREAM(NO_ERROR)`, and the program asserts that both the status and the body reach the caller.

```ada
            Sockets.Send_All
              (Socket,
               Frame_Header
                 (Reply_Block'Length, Headers_Frame, End_Headers_Flag,
                  Opened) & Reply_Block &
               Frame_Header (8, Data_Frame, End_Stream_Flag, Opened) &
                 Text_Bytes ("rejected") &
               Frame_Header (4, Reset_Stream_Frame, 0, Opened) & U32 (0),
               Timeout => 10.0);
```

Output:

```
  note   client raised FLYOLOGY.HTTP.PROTOCOL_ERROR: HTTP/2 response stream failed before body completion
  note   status 413 body ""
  ok   the complete 413 response survives RST_STREAM(NO_ERROR)
  FAIL the buffered response body is delivered
         expected: [rejected]
         actual:   []
checks: 2  failures: 1
```

The status line survives. The eight body octets that had already arrived are discarded and the read raises.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

A RST_STREAM whose error code is NO_ERROR, arriving after the response has ended with END_STREAM, must not discard the response. The buffered body should be delivered to completion and the read should report the normal end of the body, as RFC 9113 section 8.1 requires.

## Suggested treatment

`Reset_Stream` should leave a stream whose response already completed alone. The narrow form is to return early when the stream has `Remote_End` set, or when `Phase = Complete`, before touching `Failure` and `Phase`; that covers the RFC 9113 section 8.1 case exactly and leaves the behaviour for a reset arriving mid-response unchanged. The alternative is to keep marking the stream but make `Read` deliver `Response_Count` bytes before it reports a failure, which also improves the case of a genuine reset that arrives after a partial body; the two can be combined.

A reset with a non-NO_ERROR code arriving after a complete response is a separate question: RFC 9113 section 8.1 only names NO_ERROR, so treating other codes as a stream failure is defensible. This needs a maintainer decision, because it fixes the observable behaviour of a public read operation and the key is not derivable from the existing contracts. The options are: a stream-phase test inside `Reset_Stream`; an error-code test inside `Reset_Stream`; both together; a reordering of the tests in `Read` so buffered data always wins; or a new stream phase that distinguishes "complete and reset" from "failed", which introduces a new variant and so falls under "Decision authority" and "Ada interface values". Do not treat this issue as authorising any of them.

The regression test belongs in the existing HTTP/2 client integration suite: extend the `early-final-body` scenario in `tests/http2_peer.py:170-183` to send `connection.reset_stream(event.stream_id, ErrorCodes.NO_ERROR)` immediately after the final `send_data`, and assert the body in `tests/http2_client_integration.adb`. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

The server side of this repository never sends the frame that trips this, which is the subject of a separate report: {{ISSUE:H2-10}}.

## Severity

A complete, valid response is turned into an exception whenever the peer uses a sequence RFC 9113 explicitly permits and Go's server emits by default. A caller that posts a body to a Go HTTP/2 endpoint which rejects it without reading gets the right status and then `Protocol_Error` instead of the response body, which is usually the part it needs. It needs no unusual configuration on either side, only a peer that answers early. Deterministic. HTTP/2 only.
