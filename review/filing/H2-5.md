Title: A route body limit crossed mid-stream can never answer 413 over HTTP/2; the stream is reset with INTERNAL_ERROR
Labels: bug
Refs: none

## Summary

When a request body crosses a route's `Max_Body` after the stream is already open, `Publish_Data` records `Body_Limit_Failure` on the stream. `Queue_Response_Head` refuses every response for a stream with any failure recorded, so the routing layer's 413 raises `Device_Error`, the handler task's fallback 500 fails identically, and the stream is reset with INTERNAL_ERROR. The same router over HTTP/1.1 answers `413 Content Too Large`.

## Problem

Commit `f078732`.

Crossing the limit records a failure on the stream (`src/flyology-http-server-http_2.adb:644-651`):

```ada
         if Streams (Index).Failure = Body_Limit_Failure then
            null;
         elsif Body_Size (Data'Length) >
           Streams (Index).Body_Limit - Streams (Index).Body_Bytes
         then
            Streams (Index).Body_Bytes := Streams (Index).Body_Limit + 1;
            Streams (Index).Failure := Body_Limit_Failure;
            Streams (Index).Discarding := True;
```

`Discarding := True` on the same line shows the intent was to keep draining the body while a response is sent.

`Read_Body` reports it (`src/flyology-http-server-http_2.adb:756-757`, `elsif Streams (Slot).Failure = Body_Limit_Failure then Result := Read_Body_Too_Large;`), the backend turns that into an exception (`src/flyology-http-server-http_2.adb:1535-1536`, `when Read_Body_Too_Large => raise Payload_Too_Large;`), and routing answers it (`src/flyology-http-server-routing.adb:2091-2096`):

```ada
      when Payload_Too_Large =>
         if not X.Wire_Response_Started then
            X.Problem (413, "body-too-large", "Request body is too large");
         else
            X.Mark_Failed;
         end if;
```

That response can never be queued, because the same failure that produced it also blocks the response head (`src/flyology-http-server-http_2.adb:836-846`):

```ada
        (Slot   : Positive;
         Block  : Stream_Element_Array;
         Result : out Queue_Result) is
      begin
         if Streams (Slot).Phase = Free
           or else Streams (Slot).Failure /= No_Failure
           or else Streams (Slot).Response_Started
         then
            Result := Queue_Failed;
            return;
         end if;
```

`Queue_Head` turns the refusal into an exception (`src/flyology-http-server-http_2.adb:1645-1649`):

```ada
      Item.State.Streams.Queue_Response_Head
        (Item.Slot, Bytes.To_Array (Block), Result);
      if Result /= Queue_Accepted then
         raise Flyology.IO.Device_Error;
      end if;
```

which escapes the routing handler into the handler task, whose fallback fails the same way (`src/flyology-http-server-http_2.adb:2123-2135`):

```ada
               exception
                  when others =>
                     if not X.Wire_Response_Started then
                        begin
                           X.Problem
                             (500, "internal-server-error",
                              "Internal server error");
                        exception
                           when others => X.Mark_Failed;
                        end;
                     else
                        X.Mark_Failed;
                     end if;
```

`Mark_Failed` resets the stream with INTERNAL_ERROR. The client receives no 413 and no 500.

The limit is only discoverable mid-stream when the request declares no `content-length`, because the dispatch-time narrowing accepts it (`src/flyology-http-server-routing.adb:2029-2035`) and only later DATA can cross it.

The framework contract this breaks is the one the same router honours over HTTP/1.1 (`src/flyology-http-server-routing.adb:2211-2218`), which answers `413` with a body, and RFC 9110 section 15.5.14 defines the status for exactly this case.

No maintained suite covers it: nothing in `tests/http2_server_audit.adb`, `tests/http2_server_integration.adb` or `tests/http2_server_peer.py` exercises a route body limit over HTTP/2, and h2spec does not run application routes.

## What happens now

Spike: one route, `POST /upload` with `Body_Handling => Buffer_Body` and `Max_Body => 4096`, served through the same `Routing.Router` twice, once with `Mode => HTTP_2_Only` and once with `Mode => HTTP_1_Only`. The raw peer sends no `content-length` and then two 4096-octet DATA frames, so the limit can only be crossed inside `Publish_Data`. The program asserts that HTTP/2 answers with a response head, and checks HTTP/1.1 as a control.

```ada
   Routes.Post
     ("/upload", Upload'Access, Name => "upload",
      Policy =>
        (Routing.Default_Route_Policy with delta
           Body_Handling => App.Buffer_Body,
           Max_Body      => 4_096));
   ...
      Send_Frame
        (Socket, Headers_Frame, End_Headers_Flag, 1,
         Request_Block ("POST", "/upload"));
      delay 0.30;
      Send_Frame (Socket, Data_Frame, 0, 1, Block);
      delay 0.10;
      Send_Frame (Socket, Data_Frame, End_Stream_Flag, 1, Block);
```

Output:

```
  note   <- SETTINGS stream 0 length 18
  note   <- SETTINGS stream 0 length 0
  note   <- WINDOW_UPDATE stream 0 length 4
  note   <- WINDOW_UPDATE stream 1 length 4
  note   <- RST_STREAM stream 1 length 4
  note   the server reset the stream with error code 2 (2 is INTERNAL_ERROR)
  FAIL HTTP/2 answers an over-limit body with a response head, not a reset
  note   HTTP/1.1 control status line: HTTP/1.1 413 Content Too Large
  ok   HTTP/1.1 delivers the 413 for the same route and body
checks: 2  failures: 1
```

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

An over-limit request body should draw the same `413` over HTTP/2 that the same route produces over HTTP/1.1. A body limit is an application outcome, not a stream failure, and INTERNAL_ERROR misreports it to the peer as a server fault.

## Suggested treatment

`Body_Limit_Failure` should not block a response. The smallest fix is to stop `Queue_Response_Head` from treating it as a failure, so that the test at `src/flyology-http-server-http_2.adb:840-843` excludes `Body_Limit_Failure` while still excluding `Reset_Failure` and `Connection_Failure`. `Discarding` already keeps the stream draining while the response is written, which is what the 413 path needs. The rest of the machinery then works unchanged: `Read_Body` still reports `Read_Body_Too_Large`, routing still raises and catches `Payload_Too_Large`, and `X.Problem (413, ...)` reaches the wire.

This needs a maintainer decision, because it changes when a server stream may still produce a response and therefore what a peer observes for an over-limit upload. The options are: keep `Body_Limit_Failure` in `Failure_Kind` but exclude it at the one queue site; move the over-limit condition out of `Failure_Kind` into its own stream flag beside `Discarding`, which adds a record field rather than a new failure variant; add a new `Failure_Kind` variant that distinguishes "response still permitted" from "stream broken", which is a new variant under "Decision authority" and "Ada interface values"; or leave the reset in place and document that HTTP/2 answers an over-limit body with RST_STREAM, which contradicts the HTTP/1.1 behaviour of the same router. Do not treat this issue as authorising any of them.

While the response head is blocked, `Queue_Head` raising `Flyology.IO.Device_Error` out of a routing handler is what turns a route outcome into a handler crash; whichever option is chosen, the fallback at `:2123-2135` should not be the thing that decides what the peer sees.

The regression test belongs in the existing HTTP/2 server integration suite (`tests/http2_server_integration.adb`) with a route carrying `Max_Body`, and the HTTP/1.1 control asserted beside it so the two engines stay in step. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Any route that sets a body limit answers an over-limit upload with a reset instead of a 413 whenever the request does not declare its length, which is the ordinary shape of a chunked or streamed upload. The client learns only that the server had an internal error. The two engines disagree for the same router and the same route, so the behaviour depends on which protocol the client negotiated. Deterministic. HTTP/2 only.
