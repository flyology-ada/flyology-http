Title: Zero-increment WINDOW_UPDATE on an idle stream draws RST_STREAM and advances the server's last client stream
Labels: bug
Refs: none

## Summary

`Window_Update` reports a stream failure for any non-zero stream with a zero increment and returns before any idle check. The frame handler then calls `Reject_Stream`, which for a stream with no slot advances `Last_Client_Stream`, sends RST_STREAM on that idle stream and reports the frame as accepted. Three rules break at once: the frame should be a connection error, RST_STREAM must not be sent for an idle stream, and the advanced identifier makes the next legitimate request on a lower stream fail the connection.

## Problem

Commit `f078732`.

`Window_Update` returns before it can know whether the stream is idle (`src/flyology-http-server-http_2.adb:1217-1221`):

```ada
         Accepted := Increment > 0;
         Stream_Failure := False;
         if not Accepted then
            Stream_Failure := Stream_ID /= 0;
            return;
```

The frame handler treats that as a stream-scoped rejection (`src/flyology-http-server-http_2.adb:2533-2541`):

```ada
               State.Streams.Window_Update
                 (Header.Stream_ID, Increment, Accepted, Stream_Failure);
               if not Accepted and then Stream_Failure then
                  State.Streams.Reject_Stream
                    (Header.Stream_ID, Error, Slot, Accepted);
                  if Slot /= 0 and then Backends_By_Slot (Slot) /= null then
                     Backends_By_Slot (Slot).Token.Request;
                  end if;
               end if;
```

`Reject_Stream` accepts any odd non-zero identifier (`:1273-1274`) and, finding no slot, advances the connection's high-water mark and resets the idle stream (`src/flyology-http-server-http_2.adb:1277-1286`):

```ada
         elsif Slot = 0 then
            if Stream_ID > Last_Client_Stream then
               Last_Client_Stream := Stream_ID;
               Remember_Seen (Stream_ID);
            end if;
            Remember_Reset (Stream_ID);
            Queue_Control_Frame
              (Frames.Reset_Stream_Frame, 0, Stream_ID,
               U31_Payload (Natural (Error)));
            return;
```

Because it returns `Accepted = True`, the connection-error branch that follows (`:2543-2552`) never fires, although its own comment states the rule the code then fails to apply: "A zero increment and an idle stream are both connection PROTOCOL_ERROR cases".

RFC 9113 section 5.1, idle: "Receiving any frame other than HEADERS or PRIORITY on a stream in this state MUST be treated as a connection error (Section 5.4.1) of type PROTOCOL_ERROR." RFC 9113 section 6.4: "RST_STREAM frames MUST NOT be sent for a stream in the 'idle' state."

The non-zero-increment idle case is handled correctly, because it never reaches `Reject_Stream`, and the maintained audit pins exactly that case with a non-zero increment (`tests/http2_server_audit.adb:837-838`):

```ada
         Update_Code : constant Natural :=
           Idle_Goaway_Code (Window_Update_Frame, U32 (100));
```

so the zero-increment branch is untested there. The pinned h2spec 2.6.0 run is green at 146 of 146 and does not contradict this report either, because neither of its two nearby cases combines an idle stream with a zero increment. `http2/5_1_stream_states.go:55-66`, case 3, "idle: Sends a WINDOW_UPDATE frame", sends `conn.WriteWindowUpdate(1, 100)`, a non-zero increment, and checks it with `spec.VerifyConnectionError`. `http2/6_9_window_update.go:39-62`, case 2, "Sends a WINDOW_UPDATE frame with a flow control window increment of 0 on a stream", calls `conn.WriteHeaders(hp)` before the zero increment, so its stream is open rather than idle, and it ends with `return spec.VerifyStreamError(conn, http2.ErrCodeProtocol)`: even for an open stream the suite expects a stream error, so no case in it asks for the connection error an idle stream requires. There is also a general limit on what a green run proves about error handling: `VerifyConnectionError` (`spec/verifier.go:53-92`) sets `passed = true` on a `ConnectionClosedEvent` before it compares any GOAWAY code.

## What happens now

Spike: a raw peer connects, sends `WINDOW_UPDATE(stream 5, increment 0)` on a stream that has never carried HEADERS, and then a PING to settle whether the connection was failed at all. It then sends a legitimate request on stream 3.

```ada
      Connect_Peer (Socket, Address);
      --  Stream 5 has never carried a HEADERS frame, so it is idle.
      Send_Frame (Socket, Window_Update_Frame, 0, 5, U32 (0));
      Send_Frame
        (Socket, Ping_Frame, 0, 0,
         Stream_Element_Array'(1 .. 8 => 16#5A#));
      ...
         Send_Frame
           (Socket, Headers_Frame, End_Stream_Flag or End_Headers_Flag, 3,
            Request_Block ("GET", "/after"));
```

Output:

```
  note   <- SETTINGS stream 0 length 18
  note   <- SETTINGS stream 0 length 0
  note   <- RST_STREAM stream 5 length 4
  note   <- PING stream 0 length 8
  note   the server sent RST_STREAM on the idle stream 5
  note   the server answered the PING, so the connection survived
  FAIL a zero-increment WINDOW_UPDATE on an idle stream is a connection error
  FAIL the server never sends RST_STREAM for a stream in the idle state
  note   <- GOAWAY stream 0 length 8
  FAIL a legitimate request on stream 3 is still served afterwards
checks: 3  failures: 3
```

The PING acknowledgement is the evidence that the connection survived where it should have been failed. The GOAWAY at the end is the knock-on: `Last_Client_Stream` is now 5, so the request on stream 3 is refused as a lower identifier and the connection is failed then instead.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

A WINDOW_UPDATE on an idle stream is a connection error of type PROTOCOL_ERROR whatever its increment, and no RST_STREAM is sent for it. An idle stream identifier that arrives only on a rejected frame must not advance the connection's highest acted-upon stream.

## Suggested treatment

Test for the idle stream before the frame is treated as a stream-scoped rejection. The smallest form is to have `Window_Update` report the idle case distinctly, or to have the handler at `src/flyology-http-server-http_2.adb:2535` skip `Reject_Stream` when `State.Streams.Is_Idle (Header.Stream_ID)` and fall through to the existing connection-error branch at `:2543-2552`, which already computes the correct code for both conditions. `Reject_Stream`'s own `Slot = 0` path should not advance `Last_Client_Stream` for a stream the connection has never acted upon; that advance is what turns a diagnostic mistake into a failure for the next valid request.

The call-site form adds no constant, default or parameter; the other forms do. This needs a maintainer decision: add a distinct out parameter or result variant to `Window_Update` carrying "idle" separately from "stream failure", which is a new variant under "Decision authority" and "Ada interface values"; put the `Is_Idle` test at the frame-handler call site, which introduces nothing; or have `Reject_Stream` refuse a stream with no slot that the connection has never acted upon, which changes the meaning of its `Accepted` result. Do not treat this issue as authorising any of them.

The regression test belongs beside the existing idle-stream case in the maintained HTTP/2 server audit suite (`tests/http2_server_audit.adb:807-846`), which already reads the GOAWAY code for an idle DATA frame and an idle WINDOW_UPDATE with a non-zero increment; the zero increment is one more call to the same helper, plus an assertion that no RST_STREAM appears and that a later request on a lower stream is still served. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Self-inflicted in normal traffic: a conforming peer never sends a zero increment, so only the offending peer's own connection is poisoned, and the poisoning is visible as a later valid request being refused on the same connection rather than as data loss. The two wire-level violations are real but their observable cost falls on that peer. Deterministic. HTTP/2 only.
