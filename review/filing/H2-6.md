Title: HPACK encoder never emits the dynamic table size update required after a peer lowers SETTINGS_HEADER_TABLE_SIZE
Labels: bug
Refs: none

## Summary

`HTTP_2_Settings.Apply` stores the peer's `SETTINGS_HEADER_TABLE_SIZE` and nothing in the tree reads it. The HPACK builder has no dynamic table size update representation at all, so its declared maximum stays at the protocol default of 4096 whatever the peer asks for. RFC 7541 requires the update at the beginning of the first field section after the change. The pinned HPACK decoder rejects the bytes this crate emits, which an HTTP/2 peer reports as a COMPRESSION_ERROR connection error.

## Problem

Commit `f078732`.

The setting is stored and abandoned (`src/flyology-http-http_2_settings.adb:43-44`):

```ada
               when Header_Table_Size_Id =>
                  Item.Header_Table_Size := Value;
```

`rg -n Header_Table_Size src/` finds exactly four lines: the record field at `src/flyology-http-http_2_settings.ads:18`, the identifier constant at `src/flyology-http-http_2_settings.adb:5`, and the two lines above. There is no consumer.

The builder has two entry points and neither can emit a size update (`src/flyology-http-http_2_hpack.adb:774-777` and `:796-797`):

```ada
   procedure Add_Indexed (Item : in out Builder; Index : Positive) is
   begin
      Encode_Integer (Item, Index, 7, 16#80#);
   end Add_Indexed;
```

```ada
      Encode_Integer
        (Item, Named, 4, (if Never_Indexed then 16#10# else 0));
```

`16#80#` is the indexed representation and `16#10#`/`0` are the literal representations. The `001` prefix is never produced. `HTTP_2_Requests.Encode_Head` (`src/flyology-http-http_2_requests.adb:37-62`) and `HTTP_2_Responses.Encode_Head` (`src/flyology-http-http_2_responses.adb:35-57`) build every field section from those two calls, so every section this crate emits begins with an indexed or literal representation.

RFC 7541 section 4.2: "A change in the maximum size of the dynamic table is signaled via a dynamic table size update (see Section 6.3). This dynamic table size update MUST occur at the beginning of the first header block following the change to the dynamic table size. In HTTP/2, this follows a settings acknowledgment". RFC 7541 section 6.3: "A dynamic table size update starts with the '001' 3-bit pattern".

Both engines do acknowledge the peer's SETTINGS (`src/flyology-http-http_2_client_connection.adb:1841` and `src/flyology-http-server-http_2.adb:2433`, both `State.Streams.Queue_Settings_Ack;`), so the obligation is live from that acknowledgement onwards. It does not help that this encoder never inserts into a dynamic table: the peer's decoder cannot know that, and it enforces the declared maximum, not the used one.

The defect is symmetric. The server stores the client's `HEADER_TABLE_SIZE` through the same `Apply` call and ignores it in the same way, so a client that lowers the setting gets the same treatment from the server's responses.

No maintained suite covers it. `tests/http2_hpack_differential.py` and the HPACK smoke test exercise the decoder's handling of size updates; nothing checks the encoder's output against a lowered table size. The pinned h2spec 2.6.0 run is green at 146 of 146, but its two relevant cases drive the decoder: 4.2/1 "Sends a dynamic table size update at the end of header block" and 6.3/1 "Sends a dynamic table size update larger than the value of SETTINGS_HEADER_TABLE_SIZE".

## What happens now

Spike: apply a peer SETTINGS payload carrying `HEADER_TABLE_SIZE = 0`, which is what Envoy's `hpack_table_size`, HAProxy's `tune.h2.header-table-size` and nghttpx offer, and then encode the first request field section. The program asserts that the section begins with a dynamic table size update whose value is at or below the peer's limit.

```ada
   Settings.Apply (Peer, (0, 1, 0, 0, 0, 0), Applied);
   ...
      Block : constant Flyology.Bytes.Unbounded_Bytes :=
        Encode_Head
          (Method_Text        => "GET",
           Scheme_Text        => "http",
           Authority          => "localhost",
           Target             => "/",
           ...
      Check
        (Wire'Length > 0
           and then (Wire (Wire'First) and 2#1110_0000#) = 2#0010_0000#,
         "the first field section after the reduction begins with a " &
         "dynamic table size update (2#001xxxxx#)");
```

Output:

```
  ok   the reduction is accepted
  ok   the peer's HEADER_TABLE_SIZE is recorded as 0
  note   first field section begins 82 86 01 09 6c 6f 63 61
  FAIL the first field section after the reduction begins with a dynamic table size update (2#001xxxxx#)
  FAIL the signalled maximum is 0, at or below the peer's limit
checks: 4  failures: 2
```

Those exact bytes fed to the pinned hpack 4.2.0 decoder, the decoder python-hyper h2 4.3.0 uses, with `max_allowed_table_size = 0` as `h2/connection.py` sets it on settings acknowledgement:

```
hpack version: 4.2.0
block: 82 86 01 09 6c 6f 63 61 6c 68 6f 73 74 84
RESULT: InvalidTableSizeError: Encoder did not shrink table size to within the max
with 0x20 prefix: [(':method', 'GET'), (':scheme', 'http'), (':authority', 'localhost'), (':path', '/')]
RESULT: accepted
```

The same bytes are accepted once the required `0x20` update is prefixed. `InvalidTableSizeError` is what h2 reports as a COMPRESSION_ERROR connection error.

Host: macOS 26.6.2, arm64, GNAT via Alire. Checked against the pinned hpack 4.2.0 decoder from python-hyper h2 4.3.0.

## What should happen

After acknowledging a peer SETTINGS that lowers `SETTINGS_HEADER_TABLE_SIZE`, the first field section emitted must begin with a dynamic table size update whose value is at or below the new maximum, as RFC 7541 section 4.2 requires. Both engines owe this, because both acknowledge the setting.

## Suggested treatment

Add a size update representation to the builder, an `Encode_Integer (Item, Value, 5, 16#20#)` with the `001` prefix RFC 7541 section 6.3 defines, and make both `Encode_Head` entry points emit it first whenever a reduction has been acknowledged but not yet signalled. That requires the two engines to carry a "size update pending" flag beside `Peer_Settings` and to pass the value into `Encode_Head`, and it requires the flag to be set when `Apply` lowers `Header_Table_Size` and cleared when a section is emitted.

This needs a maintainer decision, because it adds a parameter to two public encoding entry points and fixes what value the encoder signals. The options are: signal 0 unconditionally, which is always valid for an encoder that keeps no dynamic table and needs no new value; signal `Natural'Min (peer value, 4096)`, which keeps the door open for a future dynamic table; pass the signalled maximum as a caller parameter on `Encode_Head`; make it a generic formal or a discriminant of the builder; or derive it from the `HTTP_2_Settings.State` record so the value cannot drift from the setting it answers. The encoder's own declared maximum is a policy value under "Ada interface values" whichever form it takes. Do not treat this issue as authorising any of them.

The regression test belongs in the existing HPACK differential harness (`tests/http2_hpack_differential.py`), which already has the pinned decoder in hand and can assert that a section emitted after a lowered setting decodes cleanly; the unit-level assertion belongs in the existing HPACK smoke test (`tests/flyology-http-http_2_hpack-smoke.adb`). The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Every request to a peer configured to lower or disable the HPACK dynamic table fails with a connection error, and that is a supported configuration of Envoy, HAProxy and nghttpx, and one line of application code for any h2 peer. It has not been seen because the stock default on both sides is 4096, so no reduction is signalled and no update is owed. When it does apply it applies to every field section, so no request to that peer succeeds. Deterministic. HTTP/2 only.
