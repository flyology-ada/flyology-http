Title: Server sends RST_STREAM(STREAM_CLOSED) for every DATA frame on a stream it has already reset
Labels: bug
Refs: H2-11

## Summary

`Publish_Data` answers a DATA frame on a stream with `Remote_End` set by queueing RST_STREAM(STREAM_CLOSED). The reset paths inside the server set `Remote_End` themselves, so a stream the server closed with its own RST_STREAM takes the same branch, and every frame the peer already had in flight draws another reset on a closed stream. RFC 9113 requires those frames to be minimally processed and discarded, and forbids sending non-PRIORITY frames on a closed stream.

## Problem

Commit `f078732`.

The branch does not separate half-closed (remote) from closed (`src/flyology-http-server-http_2.adb:618-631`):

```ada
         if Index = 0 then
            if Stream_ID /= 0 and then Stream_ID <= Last_Client_Stream then
               Queue_Control_Frame
                 (Frames.Reset_Stream_Frame, 0, Stream_ID,
                  U31_Payload (Natural (Frames.Stream_Closed_Error)));
               Charge_Closed_Stream (Flow_Length, Accepted);
            end if;
            return;
         elsif Streams (Index).Remote_End then
            Queue_Control_Frame
              (Frames.Reset_Stream_Frame, 0, Stream_ID,
               U31_Payload (Natural (Frames.Stream_Closed_Error)));
            Charge_Closed_Stream (Flow_Length, Accepted);
            return;
         end if;
```

Every path on which the server resets a stream itself sets `Remote_End := True` first: the handler-failure path (`src/flyology-http-server-http_2.adb:911-912`), `Reset_Stream` (`:1253-1254`) and `Reject_Stream` with a slot (`:1294-1295`) all do

```ada
            Streams (Slot).Failure := Reset_Failure;
            Streams (Slot).Remote_End := True;
```

so a stream the server closed is indistinguishable here from one the peer half-closed.

RFC 9113 section 5.1, closed: "An endpoint MUST NOT send frames other than PRIORITY on a closed stream." The same section describes the case the server is actually in: "An endpoint that sends a RST_STREAM frame on a stream that is in the 'open' or 'half-closed (local)' state could receive any type of frame ... An endpoint MUST minimally process and then discard any frames it receives in this state." The branch's response, a stream error of type STREAM_CLOSED, is what the section requires for half-closed (remote), which is the only case it is correct for.

The window accounting on the same path is right: `Charge_Closed_Stream` charges and credits the connection window, which is what keeps a reset stream with a retained body from stalling the connection.

No maintained suite asserts silence. `tests/http2_server_audit.adb:602-646` checks only the connection-window credit for closed-stream DATA and tolerates the resets, and `tests/http2_server_peer.py`'s connection-credit scenario does the same. The pinned h2spec 2.6.0 run passes `5.1/8: closed: Sends a DATA frame after sending RST_STREAM frame`, but that case sends DATA after the client's own RST_STREAM, where a STREAM_CLOSED stream error is the correct answer; it never exercises a stream the server reset.

## What happens now

Spike: a route whose handler declares `Content_Length => 1` and then writes two octets, so the engine resets the stream itself with INTERNAL_ERROR. The peer then sends three 100-octet DATA frames on that stream, which is what a peer may legitimately already have in flight, and the program asserts that no further RST_STREAM follows.

```ada
      Send_Frame
        (Socket, Headers_Frame, End_Headers_Flag, 1,
         Request_Block ("POST", "/fixed-overrun"));
      ...
      for Index in 1 .. 3 loop
         Send_Frame (Socket, Data_Frame, 0, 1, Chunk);
      end loop;
```

Output:

```
  note   <- SETTINGS stream 0 length 18
  note   <- SETTINGS stream 0 length 0
  note   <- RST_STREAM stream 1 length 4
  ok   the server resets the overrun stream (precondition)
  note   sent three DATA frames on the closed stream 1
  note   <- RST_STREAM stream 1 length 4
  note   <- RST_STREAM stream 1 length 4
  note   <- RST_STREAM stream 1 length 4
  note   (no further frames)
  note   extra RST_STREAM frames: 3, WINDOW_UPDATE frames: 0
checks: 2  failures: 1
```

Three 109-octet DATA frames produced three 13-octet RST_STREAM frames, so the output-to-input ratio is well under one and this is not an amplification defect. No WINDOW_UPDATE appeared because 300 octets is below the 8 KiB credit threshold.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

DATA arriving on a stream the server itself reset should be charged to and credited on the connection window and then discarded, with no frame sent in reply. A stream error of type STREAM_CLOSED remains correct for a stream the peer half-closed with END_STREAM and then sent DATA on.

## Suggested treatment

Separate the two states. The stream record already carries `Failure`, and the reset paths already set `Failure := Reset_Failure` on the same lines that set `Remote_End`, so the branch at `src/flyology-http-server-http_2.adb:626-631` can test it: when `Streams (Index).Failure = Reset_Failure`, call `Charge_Closed_Stream` and return without queueing anything; otherwise keep the existing RST_STREAM. The `Index = 0` branch at `:618-625` covers a stream that has already been reaped and needs the same treatment; `Remember_Reset` already records which identifiers the server reset and `Was_Reset` (`src/flyology-http-server-http_2.adb:442-452`) already queries that history, so the same distinction is available there.

This needs no new constant, default or parameter, so no maintainer decision is required.

The regression test belongs beside the existing closed-stream case in the maintained HTTP/2 server audit suite (`tests/http2_server_audit.adb:602-646`), which already counts the frames that come back: the addition is an assertion that the count of RST_STREAM frames after the server's own reset is zero, alongside the credit assertion it already makes. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

The client engine has the same shape on its own side, reported separately: {{ISSUE:H2-11}}.

## Severity

A wire-level violation with a small, bounded cost: each in-flight DATA frame draws one 13-octet reset, the ratio is below one so there is no amplification, and the read backpressure on the control backlog bounds it further. A conforming peer ignores the extra resets, so the observable effect is confined to the wire and to what a peer logs. It is reached by the ordinary sequence of a server rejecting an upload while the client is still sending. Deterministic. HTTP/2 only.
