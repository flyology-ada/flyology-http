Title: Client ignores RST_STREAM and WINDOW_UPDATE on idle streams instead of failing the connection
Labels: bug
Refs: H2-9

## Summary

`Reset_Stream` and `Window_Update` in the HTTP/2 client both begin with `Find (Stream_ID)` and return silently when it yields 0, so a RST_STREAM or WINDOW_UPDATE naming a stream the client has never opened is dropped. RFC 9113 makes both a connection error of type PROTOCOL_ERROR. `Publish_Headers` on the same stream is handled correctly, so the three frame types disagree about the idle state.

## Problem

Commit `f078732`.

`Reset_Stream` drops the frame (`src/flyology-http-http_2_client_connection.adb:1374-1378`):

```ada
         Index : constant Natural := Find (Stream_ID);
      begin
         if Index = 0 then
            return;
         end if;
```

`Window_Update` has the same three lines for a non-zero stream (`src/flyology-http-http_2_client_connection.adb:1342-1346`):

```ada
               Index : constant Natural := Find (Stream_ID);
            begin
               if Index = 0 then
                  return;
               end if;
```

`Publish_Headers` does not. It distinguishes a stream that was once open from one that never was (`src/flyology-http-http_2_client_connection.adb:1107-1111`):

```ada
         Result :=
           (if Index /= 0 or else Is_Closed (Stream_ID)
            then Publish_Accepted else Publish_Connection_Rejected);
         if Index = 0 then
            return;
```

so HEADERS on an idle stream is a connection error while RST_STREAM and WINDOW_UPDATE on the same stream are not.

RFC 9113 section 6.4: "RST_STREAM frames MUST NOT be sent for a stream in the 'idle' state. If a RST_STREAM frame identifying an idle stream is received, the recipient MUST treat this as a connection error (Section 5.4.1) of type PROTOCOL_ERROR." RFC 9113 section 5.1, idle: "Receiving any frame other than HEADERS or PRIORITY on a stream in this state MUST be treated as a connection error (Section 5.4.1) of type PROTOCOL_ERROR", which covers WINDOW_UPDATE.

### A second site, reported from reading the code

`Cancel_Stream` leaves the stream in phase `Complete` with `Remote_End` set rather than `Free` (`src/flyology-http-http_2_client_connection.adb:1642-1643`), so while the owner has not yet released the slot, `Find` still resolves it and a late in-flight response frame takes the `Remote_End` branch into `Reject_Stream` (`src/flyology-http-http_2_client_connection.adb:1115-1118`):

```ada
         if Streams (Index).Remote_End then
            Result := Publish_Stream_Rejected;
            Reject_Stream (Positive (Index));
            return;
```

`Publish_Data` has the same branch at `:1229-1241`. `Reject_Stream` returns early only for `Free | Failed`, not for `Complete` (`src/flyology-http-http_2_client_connection.adb:1066-1080`), so it sends a second RST_STREAM, this time with PROTOCOL_ERROR, on a stream the client itself already cancelled, and marks the stream `Response_Protocol_Failure`. RFC 9113 section 5.1 forbids sending non-PRIORITY frames on a closed stream and requires frames received in that state to be minimally processed and discarded, which is the same rule the server engine breaks on its own side, reported separately: {{ISSUE:H2-9}}.

This second site was not reproduced. The synchronous `Execute` path releases the slot immediately after cancelling (`src/flyology-http-client.adb:741-755`), so by the time a late frame arrives `Find` returns 0 and the frame is ignored. Reaching it needs the composable driver's deferred release (`src/flyology-http-client.adb:1066-1070`, which hands the exchange to `HTTP_2_Waiting_For_Pump` before releasing) with the late frame landing inside that window, and no deterministic way to place it was found.

The existing client scenarios cover cancellation from the owner's point of view, not the frames the client puts on the wire: `composable-cancel` and `reset-race` in `tests/http2_peer.py` and `tests/http2_client_integration.adb:540` and `:613` assert that the session survives. There is no idle-stream case for either frame type, and h2spec does not test clients.

## What happens now

Spike: the peer sends `RST_STREAM(stream 7, CANCEL)` and `WINDOW_UPDATE(stream 9, 100)` in its first flight, before the client has opened either stream, and then answers the client's request normally. The program asserts that the client fails the connection.

```ada
         --  Streams 7 and 9 are idle at the client: it has never opened
         --  them and never will before these frames arrive.
         Send_Frame (Socket, Reset_Stream_Frame, 0, 7, U32 (8));
         Send_Frame (Socket, Window_Update_Frame, 0, 9, U32 (100));
```

Output:

```
  note   the exchange returned status 200
  FAIL RST_STREAM and WINDOW_UPDATE on idle streams fail the connection
  note   RST_STREAM frames the client sent for the cancelled stream after its own CANCEL: 0
  ok   the client sends no further frame on a stream it already cancelled
checks: 2  failures: 1
```

The exchange completes with 200 as though the two frames had not arrived. The second check passes for the reason given above: on the synchronous path the slot is already released when the late frames land, so the second site is not exercised here.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

A RST_STREAM or WINDOW_UPDATE naming a stream the client has never opened, or an even-numbered stream, is a connection error of type PROTOCOL_ERROR under RFC 9113 sections 6.4 and 5.1, and should be treated the way `Publish_Headers` already treats HEADERS on such a stream.

## Suggested treatment

Give both procedures the test `Publish_Headers` already has. `Is_Closed` distinguishes a stream that was opened and has since been reaped from one that never existed, so `Find (Stream_ID) = 0 and then not Is_Closed (Stream_ID)` is the idle case, and it should be reported to the frame handler so that it reaches `Protocol_Failure` rather than returning silently. Both procedures currently have no result parameter, so carrying the verdict out means adding one, or moving the idle test to the two call sites in `Parse_Input` where `Is_Closed` is already reachable.

This needs a maintainer decision, because the first form adds an out parameter to two operations of the stream controller and the second changes where the state test lives. The options are: an `Accepted` or result out parameter on `Reset_Stream` and `Window_Update`, matching the shape the server engine uses; an idle test at the two frame-handler call sites with no signature change; or a shared query on the controller, such as the existing `Is_Closed`, called from the handler before dispatch. Do not treat this issue as authorising a new result variant without that decision.

For the second site, the fix is the same shape as the server's: `Reject_Stream` should return early for a stream in phase `Complete` as it already does for `Free | Failed`, so that a cancelled stream draws no second reset. That change can be made and unit-tested through the session object without reproducing the race.

The regression test belongs in the existing HTTP/2 client integration suite driven by `tests/http2_peer.py`, as a scenario whose first flight carries the two idle-stream frames, asserting that the exchange fails rather than succeeds; the cancelled-stream half belongs in `tests/flyology-http-http_2_client_connection-smoke.adb`, which can drive the controller directly and does not depend on the timing. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Leniency rather than harm for the reproduced part: the client accepts two frames it is required to reject, so a peer that violates the stream-state rules is not detected, and a stream-state confusion between the two endpoints goes unreported instead of closing the connection. Nothing is corrupted and no caller-visible result changes, which is why the reproduced behaviour is a low-impact conformance gap. The asymmetry with `Publish_Headers` is the part worth closing, because it means the three frame types disagree about what an idle stream is. The second site described above is code-level only and not reproduced, and this assessment does not rest on it. Deterministic. HTTP/2 only.
