Title: Server never resets a stream answered early while its request half is open, pinning the connection receive window
Labels: bug
Refs: H2-3

## Summary

A stream whose response completes while its request half is still open is never completed and never reset, because `Maybe_Complete` requires `Remote_End` and the handler task performs no drain or reset after the handler returns. The body octets already buffered for it were charged to the 65535-octet connection receive window and are credited back only as bytes leave the buffer, which for a handler that will never read them is never. Four such streams hold the whole connection window.

## Problem

Commit `f078732`.

A stream can only complete once the peer has ended its half (`src/flyology-http-server-http_2.adb:419-428`):

```ada
      procedure Maybe_Complete (Index : Positive) is
      begin
         if Streams (Index).Phase = Open
           and then Streams (Index).Remote_End
           and then Streams (Index).Local_End
           and then Streams (Index).Handler_Done
         then
            Streams (Index).Phase := Complete;
         end if;
      end Maybe_Complete;
```

When the handler returns without reading the body, the handler task queues nothing on the stream and does not reset it (`src/flyology-http-server-http_2.adb:2112-2138`): the block runs `Handle (Context, X)`, converts an unstarted response to `X.No_Content`, and then calls `State.Streams.Handler_Finished (Slot)`. `Remote_End` stays False, so the slot stays `Open`.

Meanwhile the octets the peer already sent were charged to both windows in `Publish_Data` and copied into the stream's input buffer. Credit is returned only as bytes leave that buffer, so nothing is returned for a stream no handler will read. The slot also stays counted against `Maximum_Concurrent_Streams` (`src/flyology-http-server-http_2.ads:19`, `constant Positive := 32`) until the peer resets it or `Max_Connection_Age` (`src/flyology-http-server-http_2.ads:38`, `Duration := 300.0`) ends the connection.

This is not a conformance violation. RFC 9113 section 8.1 makes the server's reply a MAY: "a server MAY request that the client abort transmission of a request without error by sending a RST_STREAM with an error code of NO_ERROR after sending a complete response". It is a resource-lifetime defect, and the MAY exists precisely so the server can recover what this one does not.

The shape is ordinary. An authentication middleware answering 401, a handler that answers without reading, and a `Reject_Body` route all produce it; the last does so through `src/flyology-http-server-applications.adb:1019-1026`:

```ada
         when Reject_Body =>
            if not Body_Complete (Item)
            then
               Item.Problem
                 (413, "body-not-accepted", "Route does not accept a body");
               return;
            end if;
```

No maintained suite covers it: the `early-final` scenarios in `tests/http2_peer.py` drive this repository's client against an early server response, and the maintained HTTP/2 server audit has no early-response-with-open-request case.

## What happens now

Spike: a handler that answers 401 without reading the body. The peer opens four streams, each with HEADERS without END_STREAM, which RFC 9113 section 8.1 permits while the server answers early, followed by 16000 octets of DATA, for 64000 octets against a 65535-octet connection window. The program asserts that the connection window is recovered, by credit or by a reset, for octets no handler will ever read.

```ada
            Send_Frame
              (Socket, Headers_Frame, End_Headers_Flag, Stream_ID,
               Request_Block ("POST", "/reject"));
            Send_Frame (Socket, Data_Frame, 0, Stream_ID, Block);
      ...
      Check
        (Connection_Credit + Resets * Upload_Size >= Streams * Upload_Size,
         "the connection receive window is recovered for body octets no " &
         "handler will ever read");
```

Output:

```
  note   sent 64000 octets across 4 streams, against a 65535-octet connection window
  note   (no further frames)
  note   responses: 4  resets: 0  connection credit returned: 0 octets
  ok   every stream receives its early response (precondition)
  FAIL the connection receive window is recovered for body octets no handler will ever read
checks: 2  failures: 1
```

All four responses arrive. No RST_STREAM and no connection credit follow. The peer is left with 1535 octets of connection window and no event that can replenish it, so any later upload on that connection stalls.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

A stream whose response is complete while its request half is still open should release what it holds: the buffered input should be credited back on the connection window and the slot should be freed, which over HTTP/2 means sending the RST_STREAM(NO_ERROR) that RFC 9113 section 8.1 provides for exactly this case, or draining and crediting the remainder of the request body.

## Suggested treatment

Give the completion path a route for the early-response case. After `Handler_Finished`, a stream with `Local_End` and `Handler_Done` set but `Remote_End` still False should either be reset with NO_ERROR, returning `Input_Count` to the connection window through the existing `Return_Connection_Credit` call that `Reset_Stream` already makes (`src/flyology-http-server-http_2.adb:1258`), or be put into a draining state that keeps crediting incoming DATA the way `Discarding` already does at `:656-657`.

This needs a maintainer decision, because the choice is an externally visible server policy: whether this server aborts a request body it will not read, as Go's server does, or accepts and discards it to the end. The options are: reset with NO_ERROR when the response completes with the request half open; set `Discarding` on that stream and keep crediting until the peer ends its half, with no bound on how long that lasts; do the same but bound it with a drain limit or a deadline, which introduces a new limit and therefore a new value under "Ada interface values"; expose the choice as a parameter of the server engine or of the route policy; or leave the behaviour and document that an early response over HTTP/2 holds its stream open until the peer resets it. Do not treat this issue as authorising any of them.

Note that resetting with NO_ERROR is the behaviour a client must tolerate, and this repository's own client currently does not: {{ISSUE:H2-3}}. The two should be fixed together, or the server change will break this repository's own client against itself.

The regression test belongs in the existing HTTP/2 server integration suite (`tests/http2_server_integration.adb`) with a route that answers without reading, asserting that the connection window is recovered; `tests/http2_server_peer.py` already has the machinery to keep uploading against the window. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

A resource-lifetime defect rather than a protocol violation: the peer gets its response, and only later uploads on the same connection suffer. Four early-answered uploads exhaust the connection receive window for the whole connection lifetime, which is 300 seconds by default, and each one also holds a slot against the advertised 32-stream limit. It is reached by an ordinary rejection pattern, an authentication middleware or a route that declines bodies, so a client that reuses one connection for several uploads can stall itself. A client that resets its own abandoned streams avoids it. Deterministic. HTTP/2 only.
