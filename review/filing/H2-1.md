Title: Client fails the connection when a server sends `SETTINGS_ENABLE_PUSH = 0`
Labels: bug
Refs: H2-7

## Summary

`HTTP_2_Settings.Apply` rejects SETTINGS identifier 0x2 from a server peer whatever its value, and the HTTP/2 client engine turns any non-accepted result into a connection failure. RFC 9113 permits a server to send `SETTINGS_ENABLE_PUSH` with the value 0 and makes only the value 1 an error. The pinned python-hyper h2 build this repository tests against sends exactly that setting from a server, so every request to an origin built on it fails permanently with `Flyology.HTTP.Protocol_Error`.

## Problem

Commit `f078732`.

The guard rejects the identifier on the peer role alone (`src/flyology-http-http_2_settings.adb:45-51`):

```ada
               when Enable_Push_Id =>
                  if Peer_Is_Server or else Value > 1 then
                     --  RFC 9113 prohibits SETTINGS_ENABLE_PUSH from a server.
                     Result := Settings_Protocol_Error;
                     return;
                  end if;
                  Item.Enable_Push := Value = 1;
```

`Peer_Is_Server` defaults to `True` (`src/flyology-http-http_2_settings.ads:34-38`), and the client engine passes that default and maps every non-accepted result to `Protocol_Failure` (`src/flyology-http-http_2_client_connection.adb:1829-1835`):

```ada
                  Settings.Apply
                    (State.Driver.Peer_Settings, Payload, Applied);
                  if Applied /= Settings.Settings_Accepted then
                     Protocol_Failure;
                  end if;
```

`Protocol_Failure` queues GOAWAY, fails every stream on the session and sets `Closing` (`src/flyology-http-http_2_client_connection.adb:1752-1761`):

```ada
      procedure Protocol_Failure
        (Error : Frames.Error_Code := Frames.Protocol_Error_Code) is
      begin
         if not State.Driver.Closing then
            State.Streams.Queue_Goaway (Error);
            State.Streams.Fail_All;
            State.Driver.Closing := True;
         end if;
         raise Stop;
      end Protocol_Failure;
```

That same call site also discards the distinction between the two settings failures, which is reported separately: {{ISSUE:H2-7}}.

The source comment states the opposite of the standard. RFC 9113 section 6.5.2, `SETTINGS_ENABLE_PUSH`: "A server MUST NOT explicitly set this value to 1. A server MAY choose to omit this setting when it sends a SETTINGS frame, but if a server does include a value, it MUST be 0. A client MUST treat receipt of a SETTINGS frame with SETTINGS_ENABLE_PUSH set to 1 as a connection error (Section 5.4.1) of type PROTOCOL_ERROR." Only the value 1 is an error, and the value 0 is the value the standard names as permitted.

A server built on the pinned python-hyper h2 4.3.0 (`tests/requirements-http2.txt`, `tests/requirements-client-differential.txt`) sends it. Driving that exact installed copy, a server-side `H2Connection.initiate_connection()` emits this first SETTINGS frame:

```
server first flight bytes: 00 00 2a 04 00 00 00 00 00 00 01 00 00 10 00 00 02 00 00 00 00 00 04 00 00 ff ff 00 05 00 00 40 00 00 08 00 00 00 00 00 03 00 00 00 64 00 06 00 01 00 00
  setting 0x01 = 4096
  setting 0x02 = 0
  setting 0x04 = 65535
  setting 0x05 = 16384
  setting 0x08 = 0
  setting 0x03 = 100
  setting 0x06 = 65536
```

The repository already works around its own defect rather than covering it. Both maintained Python peers delete the setting before the connection is initiated (`tests/http2_peer.py:124-126`):

```python
    # hyper-h2 retains the obsolete RFC 7540 server-side ENABLE_PUSH=0
    # default. RFC 9113 forbids a server from sending this setting.
    del connection.local_settings[SettingCodes.ENABLE_PUSH]
```

and `tests/http_client_differential_peer.py:99-101`:

```python
    #  hyper-h2 still defaults to the old client-only ENABLE_PUSH setting on
    #  server connections. RFC 9113 forbids a server from sending it.
    del protocol.local_settings[SettingCodes.ENABLE_PUSH]
```

Both comments misstate RFC 9113 in the same way the source comment does. With those two lines removed, every scenario in both peers would fail.

No maintained suite covers the defect. `tests/flyology-http-http_2_settings-smoke.adb:27-28` asserts it as correct:

```ada
   Apply (Item, (0, 2, 0, 0, 0, 0), Result);
   pragma Assert (Result = Settings_Protocol_Error);
```

and h2spec exercises the server role only, so it never drives this client.

## What happens now

Spike: the program checks `Apply` directly against the pinned peer's SETTINGS payload replayed byte for byte, checks that `ENABLE_PUSH = 1` from a server is still an error, and then runs the library client against a raw HTTP/2 server peer whose first SETTINGS frame carries the permitted setting and which then answers with a complete 200 response.

```ada
   Pinned_Peer_Settings : constant Stream_Element_Array :=
     (16#00#, 16#01#, 16#00#, 16#00#, 16#10#, 16#00#,
      16#00#, 16#02#, 16#00#, 16#00#, 16#00#, 16#00#,
      ...
   Apply (Item, Pinned_Peer_Settings, Result);
   Check
     (Result = Settings_Accepted,
      "Apply accepts the pinned h2 4.3.0 server's first SETTINGS payload");
   ...
         Send_Frame (Socket, Settings_Frame, 0, 0, Pinned_Peer_Settings);
```

Output:

```
  FAIL Apply accepts the pinned h2 4.3.0 server's first SETTINGS payload
  note   Apply returned SETTINGS_PROTOCOL_ERROR
  FAIL Apply accepts ENABLE_PUSH = 0 from a server peer
  note   Apply returned SETTINGS_PROTOCOL_ERROR
  ok   Apply still rejects ENABLE_PUSH = 1 from a server peer
  note   client raised FLYOLOGY.HTTP.PROTOCOL_ERROR: flyology-http-client.adb:6586
  FAIL the client serves a request to a server that sent ENABLE_PUSH = 0
checks: 4  failures: 3
```

The client answers the permitted setting with GOAWAY and `Client.Execute` raises.

Host: macOS 26.6.2, arm64, GNAT via Alire. Checked against the pinned python-hyper h2 4.3.0.

## What should happen

`Apply` should accept `SETTINGS_ENABLE_PUSH = 0` from a server and record `Enable_Push := False`, and reject only the value 1 from a server and any value above 1 from either peer, as RFC 9113 section 6.5.2 requires.

## Suggested treatment

Make the guard test the value, not the role:

```ada
               when Enable_Push_Id =>
                  if Value > 1
                    or else (Peer_Is_Server and then Value = 1)
                  then
                     Result := Settings_Protocol_Error;
                     return;
                  end if;
                  Item.Enable_Push := Value = 1;
```

Correct the comment at `src/flyology-http-http_2_settings.adb:47` at the same time, since it is what led the two test peers astray.

`tests/flyology-http-http_2_settings-smoke.adb:27-28` asserts the current wrong behaviour and must change: the payload `(0, 2, 0, 0, 0, 0)` with the default `Peer_Is_Server` becomes `Settings_Accepted` with `Item.Enable_Push = False`, and a new case with the value 1 keeps `Settings_Protocol_Error`. The end-to-end regression belongs in the existing HTTP/2 client integration suite driven by `tests/http2_peer.py`; the two `del ...local_settings[SettingCodes.ENABLE_PUSH]` lines at `tests/http2_peer.py:126` and `tests/http_client_differential_peer.py:101` should be removed so that both maintained peers present the stock server shape. The spike is the test.

No maintainer decision is needed: the accepted value and the rejected value are both fixed by RFC 9113 section 6.5.2, and no new constant, default or parameter is introduced. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Every HTTP/2 request to an origin built on python-hyper h2 fails permanently, and hypercorn and Twisted are in that set. It needs no unusual configuration on either side: the client's default `Peer_Is_Server` and the peer's default settings are enough, and the failure is a connection error that fails every multiplexed stream on the session, surfaced to the caller as `Protocol_Error`. The repository does not see it because both of its Python peers are patched around it. Deterministic. HTTP/2 only.
