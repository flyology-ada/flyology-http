Title: Cancelling a client stream mid field section abandons the CONTINUATION and freezes the connection pump
Labels: bug
Refs: none

## Summary

`Cancel_Stream` sets the stream's phase to `Complete` but leaves `Continuation_Slot` pointing at it. Every output branch of `Pull_Output` requires `Phase = Open`, and the control-output branch is skipped while `Continuation_Slot` is non-zero, so the pump can emit nothing at all afterwards: not the CONTINUATION that would terminate the field section, not the queued RST_STREAM, not a sibling stream's frames, not a SETTINGS or PING acknowledgement. The connection is left with an unterminated field section on the wire and no further output.

## Problem

Commit `f078732`.

`Cancel_Stream` queues the reset and marks the stream complete, without clearing the pin (`src/flyology-http-http_2_client_connection.adb:1629-1643`):

```ada
            --  A stream whose request field section has not entered the pump
            --  is still idle at the peer. Sending RST_STREAM for that stream
            --  would itself be a connection-level protocol error. Once any
            --  header bytes have been pulled, continuation ordering ensures
            --  the reset follows the complete field section on the wire.
            if Streams (Handle.Slot).Head_Cursor > 1 then
               Queue_Control_Frame
                 (Frames.Reset_Stream_Frame, 0,
                  Streams (Handle.Slot).ID,
                  U31_Payload (Natural (Frames.Cancel)));
               Wake_Pump := True;
            end if;
            Streams (Handle.Slot).Remote_End := True;
            Streams (Handle.Slot).Phase := Complete;
```

The comment's claim is false. The control-output branch is guarded by the pin (`src/flyology-http-http_2_client_connection.adb:719-721`):

```ada
         elsif Continuation_Slot = 0
           and then Control_Cursor <= Bytes.Length (Control_Output)
         then
```

`Required_Header_Slot` is initialised from the pin (`:679`, `Required_Header_Slot : Natural := Continuation_Slot;`), which restricts the loop at `:751-758` to that one slot, and both emitting branches in it require `Phase = Open` (`:761-762` and `:813-815`):

```ada
               elsif Item.Phase = Open
                 and then Item.Head_Cursor <= Bytes.Length (Item.Request_Head)
               then
```

The pin is cleared only by `Clear_Stream` (`:504-509`), which runs when the owner releases the stream. The synchronous path releases immediately after cancelling (`src/flyology-http-client.adb:741-755`), but the composable path defers the release until the pump reports no pending output (`src/flyology-http-client.adb:1066-1070`), which it never will while the pin holds.

The server engine handles the same case correctly, and says why (`src/flyology-http-server-http_2.adb:1031-1038`):

```ada
               --  A stream that completes while its field section is still
               --  fragmented must keep emitting: CONTINUATION frames cannot
               --  be interleaved, so abandoning the block would leave the
               --  connection output pinned to a slot that never produces
               --  again.
               if (Item.Phase = Open or else Index = Required)
                 and then Item.Response_Started
                 and then Item.Head_Cursor <= Bytes.Length (Item.Response_Head)
```

RFC 9113 section 4.3: "Field blocks MUST be transmitted as a contiguous sequence of frames, with no interleaved frames of any other type or from any other stream". RFC 9113 section 6.10: "If the END_HEADERS flag is not set, this frame MUST be followed by another CONTINUATION frame. A receiver MUST treat the receipt of any other type of frame or a frame on a different stream as a connection error (Section 5.4.1) of type PROTOCOL_ERROR." Both engines in this repository enforce that rule on receipt, so a peer that later receives any other frame on the connection fails it.

No maintained suite covers it. `tests/http2_server_audit.adb:727-799` covers the server engine's equivalent pin, not the client's, and `tests/flyology-http-http_2_client_connection-smoke.adb` contains no `Cancel_Stream` case.

## What happens now

Spike: thirty concurrent exchanges on one pooled client, each with a request head of roughly 32 KiB so that every head needs a HEADERS fragment and a CONTINUATION, against a peer whose accepted socket receive buffer is capped and which drains slowly, so the pump parks on `Need_Write` while a field section is in flight. The three-second exchange deadlines then expire mid-section. The program captures everything the peer receives and asserts that no field section is left unterminated.

```ada
            Client.Set_Target (Ask, "/pinned/" & (1 .. 15_900 => 'p'));
            Client.Add_Header (Ask, "x-large", (1 .. 16_000 => 'x'));
            declare
               Reply : Client.Response :=
                 Client.Execute (Session, Ask, Timeout => 3.0);
```

Output, showing the last nine frames of the capture:

```
  note   -> HEADERS stream 41 length 16384 (no END_HEADERS)
  note   -> CONTINUATION stream 41 length 15559 END_HEADERS
  note   -> HEADERS stream 43 length 16384 (no END_HEADERS)
  note   -> CONTINUATION stream 43 length 15559 END_HEADERS
  note   -> HEADERS stream 45 length 16384 (no END_HEADERS)
  note   -> CONTINUATION stream 45 length 15559 END_HEADERS
  note   -> HEADERS stream 47 length 16384 (no END_HEADERS)
  note   -> CONTINUATION stream 47 length 15559 END_HEADERS
  note   -> HEADERS stream 49 length 16384 (no END_HEADERS)
  note   !! the capture ends inside the field section of stream 49: its CONTINUATION was never emitted
  note   captured 783484 octets in 50 complete frames
  FAIL a cancelled request never leaves its field section unterminated on the wire
checks: 1  failures: 1
```

After that HEADERS frame the spike waits thirteen further seconds, issues one more request on the same pooled client, and lets the peer drain to end of stream. Nothing more arrives. The capture ends on a clean frame boundary: no CONTINUATION for stream 49, no RST_STREAM for any of the twenty-five cancelled streams, no field section for streams 51 to 59, and nothing for the follow-up request. No interleaved frame was observed, because the session emitted no frame of any kind after the cancel.

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

A stream cancelled while its field section is fragmented must still emit the CONTINUATION frames that terminate the section, and only then the RST_STREAM, so that the connection returns to a state where other streams and control frames can be sent. That is what RFC 9113 sections 4.3 and 6.10 require of the sender, and it is what the server engine in this repository already does.

## Suggested treatment

Give the client's `Pull_Output` the exemption the server's already has: admit the pinned slot regardless of phase, so that the branch at `src/flyology-http-http_2_client_connection.adb:813-815` becomes the equivalent of `(Item.Phase = Open or else Index = Required_Header_Slot)`. The remaining head bytes are still in `Request_Head` and `Head_Cursor` still points into them, so the section finishes and the pin clears through the existing path at `:802` and `:852`; the queued RST_STREAM then leaves on the following pull. Correct the comment at `:1630-1634` at the same time, since it records an invariant the code does not hold.

Clearing the pin inside `Cancel_Stream` instead would be wrong: it would let the next pull emit a different stream's frame directly after an unterminated HEADERS, which is the connection error RFC 9113 section 6.10 names.

This needs no new constant, default or parameter, so no maintainer decision is required. The regression test belongs in the existing HTTP/2 client connection smoke test (`tests/flyology-http-http_2_client_connection-smoke.adb`), which can drive the session object directly: open a stream with a head larger than one frame, pull once, cancel, and assert that the next pull yields the CONTINUATION with END_HEADERS and then the RST_STREAM. The end-to-end shape belongs beside the existing `continuation` scenario in `tests/http2_client_integration.adb`. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

One cancelled or timed-out request silently stops all output on a shared HTTP/2 connection, including other exchanges multiplexed on it and the acknowledgements the peer is waiting for, until the owner happens to release that stream or the connection deadline ends it; under the composable driver the release is itself waiting on the pump, so the freeze persists. The wire is left with a field section that no conforming peer may see followed by any other frame. Reaching it needs write backpressure concurrent with a cancellation, which had to be arranged here with a deliberately slow peer and is not the common case on a fast link, but a slow peer, a `Need_Write` transport, or an ordinary deadline expiry on a large request head is enough. Deterministic under those conditions. HTTP/2 only.
