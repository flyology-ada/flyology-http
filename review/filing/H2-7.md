Title: `SETTINGS_INITIAL_WINDOW_SIZE` above 2^31-1 is answered with PROTOCOL_ERROR instead of FLOW_CONTROL_ERROR
Labels: bug
Refs: H2-1

## Summary

`HTTP_2_Settings.Apply` distinguishes an oversized `SETTINGS_INITIAL_WINDOW_SIZE` and returns `Settings_Flow_Control_Error`, but both frame handlers collapse every non-accepted result into `Protocol_Failure`, whose error code defaults to PROTOCOL_ERROR. RFC 9113 requires FLOW_CONTROL_ERROR. Both the server and the client engine send 0x1 where 0x3 is required.

## Problem

Commit `f078732`.

The settings unit gets it right (`src/flyology-http-http_2_settings.adb:54-58`):

```ada
               when Initial_Window_Size_Id =>
                  if Value > 16#7FFF_FFFF# then
                     Result := Settings_Flow_Control_Error;
                     return;
                  end if;
```

The server's frame handler throws the distinction away (`src/flyology-http-server-http_2.adb:2422-2427`):

```ada
                  Settings.Apply
                    (Peer_Settings, Payload, Applied,
                     Peer_Is_Server => False);
                  if Applied /= Settings.Settings_Accepted then
                     Protocol_Failure;
                  end if;
```

`Protocol_Failure` defaults its argument to `Frames.Protocol_Error_Code`. The client's handler has the identical shape (`src/flyology-http-http_2_client_connection.adb:1831-1835`), the same call site as {{ISSUE:H2-1}}. Four lines further on the server does pass the right code for the adjacent overflow case (`src/flyology-http-server-http_2.adb:2431`, `Protocol_Failure (Frames.Flow_Control_Error);`), so the value is available and only this path loses it.

RFC 9113 section 6.5.2, `SETTINGS_INITIAL_WINDOW_SIZE`: "Values above the maximum flow-control window size of 2^31-1 MUST be treated as a connection error (Section 5.4.1) of type FLOW_CONTROL_ERROR."

The existing coverage stops at the unit. `tests/flyology-http-http_2_settings-smoke.adb:35-36` asserts the result of `Apply` and never reaches an engine:

```ada
   Apply (Item, (0, 4, 16#80#, 0, 0, 0), Result);
   pragma Assert (Result = Settings_Flow_Control_Error);
```

The pinned h2spec 2.6.0 run does exercise the engine and reports `6.9.2/3: Sends a SETTINGS_INITIAL_WINDOW_SIZE settings with an exceeded maximum window size value` as passing, in a run of 146 tests with 146 passed. That result does not contradict this report, because h2spec accepts the close without looking at the code. `VerifyConnectionError` (`spec/verifier.go:53-92`) is:

```go
	passed := false
	for !conn.Closed {
		ev := conn.WaitEvent()

		switch event := ev.(type) {
		case ConnectionClosedEvent:
			passed = true
		case GoAwayFrameEvent:
			passed = VerifyErrorCode(codes, event.ErrCode)
```

A `ConnectionClosedEvent` sets `passed` before any GOAWAY code is compared, and the loop breaks on it. A green h2spec run therefore vouches for the fact that the connection was failed, not for the error code it was failed with, for this case or any other connection-error case in the suite.

## What happens now

Spike: a raw peer sends `SETTINGS` with identifier 4 and value `16#8000_0000#` to the server engine, and a raw peer sends the same frame to the library client; the program reads the GOAWAY from each and asserts the error code is 3.

```ada
   Oversized : constant Stream_Element_Array :=
     (0, 4, 16#80#, 0, 0, 0);
   ...
      Connect_Peer (Socket, Address, Oversized);
   ...
         Send_Frame (Socket, Settings_Frame, 0, 0, Oversized);
```

Output:

```
  note   server GOAWAY error code 1
  FAIL the server answers an oversized INITIAL_WINDOW_SIZE with FLOW_CONTROL_ERROR (0x3)
         expected: 3   actual: 1
  note   client GOAWAY error code 1
  FAIL the client answers an oversized INITIAL_WINDOW_SIZE with FLOW_CONTROL_ERROR (0x3)
         expected: 3   actual: 1
checks: 2  failures: 2
```

Host: macOS 26.6.2, arm64, GNAT via Alire.

## What should happen

Both engines should close with GOAWAY carrying FLOW_CONTROL_ERROR (0x3) for a `SETTINGS_INITIAL_WINDOW_SIZE` above 2^31-1, as RFC 9113 section 6.5.2 requires, and keep PROTOCOL_ERROR for the settings failures that call for it.

## Suggested treatment

Carry the result through instead of discarding it at both sites: at `src/flyology-http-server-http_2.adb:2425-2427` and `src/flyology-http-http_2_client_connection.adb:1833-1835`, pass `Frames.Flow_Control_Error` when `Applied = Settings.Settings_Flow_Control_Error` and keep the default otherwise. `Apply_Result` already carries the distinction, so nothing new is introduced and no maintainer decision is needed.

The regression test belongs in the existing HTTP/2 server audit suite (`tests/http2_server_audit.adb`), which already reads GOAWAY error codes for other cases, with the client half beside the existing client connection smoke test. The unit-level assertion at `tests/flyology-http-http_2_settings-smoke.adb:35-36` stays as it is; it is correct and it is not what is broken. The spike is the test. The change is outside every unit `./scripts/prove.sh` proves.

## Severity

Diagnostic impact only: a conforming peer closes the connection either way, and the wrong code changes what it logs rather than what it does. It needs a peer that sends an out-of-range setting, which a conforming peer does not do. The reason to fix it is that the pinned conformance run cannot see it, so the same class of error-code defect can accumulate unnoticed in both engines. Deterministic. HTTP/2 only.
