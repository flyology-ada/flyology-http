Title: Server enforces its reduced 16 KiB stream window before the peer can have processed the SETTINGS that announced it
Labels: bug
Refs: none

## Summary

Every server stream starts with a receive window of 16384 octets, the value the server advertises in its own SETTINGS, and `Publish_Data` consumes against it from the first DATA frame. A peer that has not yet processed that SETTINGS frame must use the protocol default of 65535, so it legitimately sends more. The server answers with GOAWAY(FLOW_CONTROL_ERROR), which fails every stream on the connection. Stock curl posting 20 KiB to this server is killed this way.

## Problem

Commit `f078732`.

The initial per-stream receive window is the advertised value (`src/flyology-http-server-http_2.adb:99-101`):

```ada
      Send_Window    : Policy.Window_Size := 65_535;
      Receive_Window : Policy.Window_Size :=
        Policy.Window_Size (Settings.Advertised_Initial_Window_Size);
```

`Advertised_Initial_Window_Size` is 16384 (`src/flyology-http-http_2_settings.ads:14-15`). The connection window is left at the protocol default (`src/flyology-http-server-http_2.adb:209`, `Connection_Receive_Window : Policy.Window_Size := 65_535;`), so only the stream window is reduced.

`Publish_Data` consumes against that window from the very first frame, and a refusal returns with `Accepted` still False (`src/flyology-http-server-http_2.adb:633-641`):

```ada
         Connection_Result := Policy.Consume
           (Connection_Receive_Window, Policy.Data_Length (Flow_Length));
         Stream_Result := Policy.Consume
           (Streams (Index).Receive_Window,
            Policy.Data_Length (Flow_Length));
         if not Connection_Result.Accepted or else not Stream_Result.Accepted
         then
            return;
         end if;
```

The frame handler escalates that refusal to a connection error (`src/flyology-http-server-http_2.adb:2513-2521`):

```ada
               if not Accepted then
                  --  RFC 9113 5.1: a frame other than HEADERS or PRIORITY on
                  --  an idle stream is a connection PROTOCOL_ERROR. Only a
                  --  genuinely exhausted window is FLOW_CONTROL_ERROR.
                  Protocol_Failure
                    ((if State.Streams.Is_Idle (Header.Stream_ID)
                      then Frames.Protocol_Error_Code
                      else Frames.Flow_Control_Error));
               end if;
```

RFC 9113 section 6.9.3: "A receiver that wishes to use a smaller flow-control window than the current size can send a new SETTINGS frame. However, the receiver MUST be prepared to receive data that exceeds this window size, since the sender might send data that exceeds the lower limit prior to processing the SETTINGS frame." The same section states the strongest permitted response: "The receiver MAY instead send a RST_STREAM with an error code of FLOW_CONTROL_ERROR for the affected streams." A connection error is not among the permitted responses.

The server also has no way to know when its reduced window became binding, because it ignores the peer's SETTINGS acknowledgement entirely (`src/flyology-http-server-http_2.adb:2417-2418`): the SETTINGS branch is guarded by `if (Header.Flags and Frames.Ack_Flag) = 0 then` and has no else.

No maintained suite sends more than the reduced window before the server's SETTINGS is processed. `tests/http2_server_peer.py:128-137` sends only what the acknowledged window allows:

```python
            available = min(
                self.connection.local_flow_control_window(stream_id),
                self.connection.max_outbound_frame_size,
                len(body) - offset,
            )
```

The maintained HTTP/2 server audit's flow-control cases stay at or below the reduced window, and the 20 KiB upload in `tests/http2_server_integration.adb` uses this repository's own client over loopback, where the server's SETTINGS wins the race. The pinned h2spec 2.6.0 run reports 146 of 146 passing, but none of its cases sends over-window DATA before processing the server's SETTINGS: 6.9.1/1 sets the peer's initial window to 1 and checks the server's sending side, and 6.9.2/1 changes `SETTINGS_INITIAL_WINDOW_SIZE` mid-connection.

## What happens now

Spike: a raw peer connects, sends its preface and its own empty SETTINGS, and then writes HEADERS with `content-length: 20480` followed by DATA(16384) and DATA(4096, END_STREAM) without ever reading the server's SETTINGS, which is exactly the state of a conforming sender that has not processed it. The program asserts that this is not a connection error.

```ada
      Connect_Peer (Socket, Address);
      Send_Frame (Socket, Headers_Frame, End_Headers_Flag, 1, Head);
      Send_Frame (Socket, Data_Frame, 0, 1, First_Burst);
      Send_Frame (Socket, Data_Frame, End_Stream_Flag, 1, Second_Burst);
```

Output:

```
  note   <- SETTINGS stream 0 length 18
  note   <- SETTINGS stream 0 length 0
  note   <- GOAWAY stream 0 length 8
  note   GOAWAY error code 3 (0x3 is FLOW_CONTROL_ERROR, 0x1 is PROTOCOL_ERROR)
  FAIL 20480 octets of DATA sent before the peer could process the server's reduced SETTINGS is not a connection error
checks: 1  failures: 1
```

The same program run with the single argument `serve` holds one loopback HTTP/2 server open. Stock curl posting a 20480-octet file to it is killed:

```
} [20480 bytes data]
* upload completely sent off: 20480 bytes
* received GOAWAY, error=3, last_stream=1
* Recv failure: Connection reset by peer
* Failed receiving HTTP2 data: 56(Failure when receiving data from the peer)
curl exit: 56
```

Host: macOS 26.6.2, arm64, GNAT via Alire. Checked against curl 8.7.1 with nghttp2 1.68.1.

## What should happen

A peer that exceeds the reduced window before it can have processed the SETTINGS that announced it must not lose the connection. RFC 9113 section 6.9.3 requires the receiver to be prepared for that data, and permits at most a stream error of type FLOW_CONTROL_ERROR for the affected stream.

## Suggested treatment

The mechanical part is to stop starting the stream receive window below the protocol default, and to stop escalating a refused stream-window consume to a connection error. The second half is straightforward: in the `not Accepted` branch at `src/flyology-http-server-http_2.adb:2513-2521`, a stream that is not idle and whose connection window is intact should draw `RST_STREAM(FLOW_CONTROL_ERROR)` on that stream instead of `Protocol_Failure`, which needs `Publish_Data` to report which of the two windows refused.

The first half is not mechanical, because the per-stream input buffer is derived from the same value (`src/flyology-http-server-http_2.adb:51-52`):

```ada
   Stream_Buffer_Capacity : constant Positive :=
     Positive (Settings.Advertised_Initial_Window_Size);
```

Raising the window alone would move the failure rather than remove it: `Publish_Data` returns without accepting when the buffer would overflow (`:658-661`), which reaches the same `Protocol_Failure`.

This needs a maintainer decision, because it sets an externally visible receive policy and a buffer bound, and `Advertised_Initial_Window_Size` is a visible constant in an `.ads` file. The options are: keep the advertised value at 16384 but start each stream at the protocol default 65535 and apply the reduction only once the peer's SETTINGS acknowledgement has been observed, which also requires the ignored ACK at `:2417-2418` to be tracked, and requires the input buffer to be sized for the larger window; stop advertising a reduced `SETTINGS_INITIAL_WINDOW_SIZE` at all and keep the protocol default, with the buffer sized to match; make the advertised window and the buffer bound a caller parameter or a discriminant of the server engine rather than a fixed value; derive the buffer bound from the window value by contract so the two cannot drift; or keep the reduced window and treat the overshoot as a stream error only, accepting that the excess octets are discarded. Do not treat this issue as authorising any of them.

The regression test belongs in the existing HTTP/2 server audit suite (`tests/http2_server_audit.adb`), beside its other flow-control cases, and `tests/http2_server_peer.py` should gain an upload scenario that writes its first flight without waiting for the server's SETTINGS. The spike is the test. The window arithmetic itself lives in `Flyology.HTTP.HTTP_2_Policy`, which `./scripts/prove.sh` proves; if the fix touches that unit it must keep discharging with `--checks-as-errors=on`.

## Severity

A stock client that pipelines a request body larger than 16 KiB loses the whole connection, and every multiplexed stream on it, on the server's default configuration. curl with nghttp2 does this for an ordinary 20 KiB POST, so it is reachable without any unusual peer or setting. The loopback suites do not see it because the server's SETTINGS frame arrives before the client's second DATA frame; any real network latency loses that race. Deterministic. HTTP/2 only.
