Parse identifiers once, then use their parts deliberately.

flyology_iri separates RFC URI/IRI references from WHATWG URL behavior and turns a normalized endpoint into the origin and request target expected by Flyology HTTP.

flyology_iri is a separate Alire crate in this repository. It has no Flyology runtime dependency, so URI and URL parsing can also be used by non-HTTP code.

IDENTIFIERS 01

Choose semantics before parsing.

The parser does not blur three different contracts. Select URI_Syntax for RFC 3986 ASCII references, IRI_Syntax for RFC 3987 references containing well-formed UTF-8, or Web_URL_Syntax for browser-style URL parsing and serialization.

URI_Syntax
Validate absolute or relative RFC 3986 references. Percent escapes must contain two hexadecimal digits.
IRI_Syntax
Apply the reference grammar while accepting well-formed UTF-8 in IRI component positions.
Web_URL_Syntax
Normalize special and non-special URLs, IDNA hosts, IPv4 and IPv6 literals, dot segments, default ports, and file: paths. It can resolve input against a parsed web base URL.

Use web mode for an HTTP or WebSocket endpoint supplied as one URL. Use URI or IRI mode when the value is a protocol-neutral reference and browser URL normalization would be the wrong contract.

IDENTIFIERS 02

Keep one owned serialization and component spans.

Reference owns the normalized serialization once and records offsets for scheme, authority, user information, host, port, path, query, and fragment. Component getters return strings; Has_Query and Has_Fragment distinguish an absent delimiter from a present empty component.

Web parsing lowercases schemes and domains, applies IDNA/Punycode, canonicalizes IP literals and ports, percent-encodes required bytes, and preserves the URL distinction between hierarchical and opaque paths. Image is the canonical serialization; it is not necessarily byte-for-byte equal to the input.

IDENTIFIERS 03

Derive the HTTP origin and target from the same URL.

Flyology's HTTP client intentionally accepts an origin at configuration time and an origin-form target on each request. Parse a complete endpoint once, then use Origin and Target to cross that boundary without hand-splitting strings.

Origin accepts parsed http, https, ws, and wss URLs. It returns only the normalized scheme, host, and optional nondefault port; URL credentials are deliberately omitted. Target returns the normalized path and optional query, including a present empty query, and deliberately omits the fragment. Both raise Malformed_Reference when the reference cannot represent this network-URL boundary.

!

Parsing a URL does not authorize its destination. Apply application policy to Scheme, Host, and Port before configuring a client when input is untrusted. URL normalization neither prevents SSRF nor chooses a trust boundary, and it does not make credentials safe to transmit.

IDENTIFIERS 04

Use the same adapters for WebSocket handshakes.

A WebSocket endpoint has a ws or wss connection origin plus a request target. The optional browser Origin header is a separate HTTP(S) application origin. Parse those values separately so their roles stay visible.

Set_Origin sets the browser-origin handshake field; it does not select the socket destination. Keep it absent for a non-browser client unless the server policy requires one, and never copy an endpoint's wss: origin into that HTTP-origin field.

IDENTIFIERS 05

Resolve with the semantics of the selected mode.

The Parse (Input, Base) overload applies WHATWG URL resolution, including special-scheme slash handling and file: drive-letter rules. For RFC URI or IRI references, call Resolve (Base, Relative); that path follows RFC 3986 section 5.2 rather than the browser state machine.

IDENTIFIERS 06

Choose exceptions, diagnostics, or a Boolean fast path.

Parse raises Malformed_Reference. Try_Parse returns a stable error category and can reuse the destination's owned-string capacity. Diagnose reports the first error and byte offset for URI/IRI grammar checks. Can_Parse avoids constructing a reference; common absolute HTTP(S), URI, and IRI validation paths do not allocate, while less common web inputs may allocate during normalization or IDNA handling.

Keep a finite Max_Length at untrusted boundaries. It bounds input for validation and the resulting serialization for construction; normalization can make a serialized URL longer than its source.

IDENTIFIERS 07

Keep conformance and performance claims pinned.

The maintained parser harness compares failure, canonical href, protocol, credentials, host and hostname, port, pathname, search, and hash against all 919 parsing cases in Ada URL 4.0.0's pinned WHATWG data. The exact ada-url/url-dataset benchmark contains 100,025 nonempty inputs; both implementations accept 99,999.

On the recorded Apple M3 Max development run, five independent ten-corpus repetitions produced medians of 20 ns per URL for Flyology validation versus 19 ns for Ada URL, and 103 ns for Flyology parse-plus-href versus 104 ns for Ada URL. These figures establish local parity on that pinned workload, not portable performance or production qualification. Reproduce the revisions and commands from the repository's flyology_iri/BENCHMARKS.md.

flyology_iri is experimental. Treat normalization, destination policy, and input bounds as separate application decisions.
