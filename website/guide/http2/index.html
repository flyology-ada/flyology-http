Select HTTP/2 without changing application code.

Clients keep the ordinary request API. Servers keep the same exchange, routes, middleware, body policies, and synchronous response helpers.

i

HTTP/2 is opt-in. Existing Configure calls keep HTTP/1.1-only behavior, so adding this version does not silently change an application's transport policy.

HTTP/2 01

Choose the failure behavior you need.

Pass a Client.Protocol_Mode to an explicit Configure overload. The mode determines whether the client may fall back and whether TLS is required.

HTTP_1_Only
Use HTTP/1.1 and do not offer HTTP/2. This is the behavior of existing overloads.
Negotiate_HTTP_2
For an HTTPS origin, offer h2 and then http/1.1 through ALPN. Use HTTP/1.1 when the authenticated peer does not select HTTP/2.
Require_HTTP_2
For an HTTPS origin, require the peer to select h2. Any other ALPN result fails the connection.
HTTP_2_Prior_Knowledge
For an http:// origin, send the HTTP/2 connection preface directly. The client does not perform the deprecated HTTP/1.1 Upgrade handshake.

Use negotiation for general HTTPS clients, requirement when HTTP/2 is part of the service contract, and prior knowledge only when the cleartext endpoint is already known to speak HTTP/2.

HTTP/2 02

Configure authenticated TLS and ALPN.

Initialize a TLS provider normally, then pass the provider, mode, and pool policy to Configure. Certificate-chain and hostname verification remain enabled. The provider must support ALPN for either HTTP/2 negotiation mode.

Replace Negotiate_HTTP_2 with Require_HTTP_2 to reject fallback. Supplying a negotiation mode for cleartext HTTP, or prior knowledge for HTTPS, is rejected during configuration.

HTTP/2 03

Use the ordinary client API.

Requests do not select their own protocol. Build a normal Client.Request, call Execute, and consume the limited response before it leaves the client's lifetime. The selected protocol is available on the response.

Concurrent callers may share the configured client. On HTTP/2, up to 32 active streams can share one transport, subject to the peer's advertised stream limit. Pool Capacity still bounds open plus connecting transports, while each transport can carry several exchanges. Admission waits, timeouts, cancellation, GOAWAY handling, safe retries, and explicit shutdown retain their normal client semantics.

A response continues to own one exchange lease. Reading it to completion releases its stream for reuse. Finalizing an incomplete HTTP/2 response resets that stream instead of discarding unrelated streams on the same connection.

HTTP/2 04

Use prior knowledge only for a known cleartext peer.

!

Prior knowledge provides no transport authentication or confidentiality. Use it for a controlled cleartext hop whose protocol is known in advance. It does not probe for HTTP/1.1 and cannot fall back after sending the HTTP/2 preface.

HTTP/2 05

Exercise a peer with the showcase client.

The maintained curl-like CLI exposes the same policies. Verbose output prints both the requested policy and the protocol selected for the response.

--ca-file selects an additional certificate authority file for a private test endpoint. There is no option to disable certificate or hostname verification.

HTTP/2 06

Reuse the high-level server API.

The existing Routing.Serve has an accepted-connection overload that selects HTTP/1.x, HTTP/2, or ALPN. Route registration, middleware, body policy, parameters, deadlines, response helpers, streamed bodies, and SSE remain unchanged. Each admitted HTTP/2 stream runs its synchronous handler in a lightweight task while one connection pump owns framing and flow control.

The TLS provider for this example offers h2 and http/1.1. ALPN_Negotiated reads the selected protocol and invokes the appropriate engine, so both protocols use the same registered routes on port 8443. HTTP_2_Only instead accepts a cleartext prior-knowledge connection or TLS already selected as h2. HTTP_1_Only preserves explicit HTTP/1.x behavior.

The listening port is configured before this call, when the application binds its Flyology socket. Routing.Serve receives an already accepted connection, so changing the protocol mode does not move listener ownership or port configuration into the router.

!

The raw connection API is intentionally not drop-in. Server.Connection contains HTTP/1.x connection-scoped parser and response state. HTTP/2 has several independently blocked streams on one connection, so direct low-level HTTP/2 users implement the generic HTTP_2 application callback with Applications.Exchange instead.

HTTP/2 07

Keep the current boundary visible.

Request bodies
Empty and retained request bodies are supported. Borrowed streaming body sources, request trailers, and Expect: 100-continue remain HTTP/1.1-only.
Responses
Response heads and bodies remain bounded and streamable through the ordinary API. HTTP/2 has no reason phrase, so Reason_Phrase returns an empty string.
Server features
The application server supports prior knowledge or an already ALPN-selected connection, up to 32 concurrent streams, bounded per-stream buffers, routing, middleware, streaming bodies, and SSE. The accepted-connection Ingress budget currently applies only to HTTP/1.x; HTTP/2 request retention is bounded by its fixed stream buffers and route body limits. The server does not provide server push, extended CONNECT/WebSockets, h2c Upgrade, or protocol fallback after a connection has started.
Intermediaries
Proxying and content decoding are not implemented.

The implementation is experimental. The API and tests establish bounded behavior, but they do not constitute a production-qualification claim.

HTTP/2 08

Run the maintained qualification commands.

all runs codecs, the deterministic python-hyper/h2 client matrix, showcase CLI coverage, the routed HTTP/2 server test, and an independent python-hyper/h2 peer against the server over prior knowledge and TLS ALPN. The explicit h2spec target runs the pinned h2spec 2.6.0 image against a concurrent cleartext server adapter; the maintained baseline is 146 of 146 tests passing. qualification adds client interoperability, fragmentation and reset campaigns, concurrent multi-epoch resource checks in both task lanes, and h2spec. This evidence supports the experimental implementation but is not a production-qualification claim. See the repository's HTTP/2 conformance notes for the maintained evidence boundary.

Flyology HTTP is experimental. Validate the exact peer, TLS provider, workload, and operating constraints for your application.
